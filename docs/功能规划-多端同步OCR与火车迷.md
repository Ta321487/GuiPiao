# 功能规划：多端同步、OCR 导入与火车迷向能力

> 状态：规划稿（未全部开工）  
> 背景：PC 端 GuiPiao 已具备行程 CRUD、统计、地图、票面预览/导出、备份等；采集侧仍偏「坐在电脑前手填」。  
> 本文汇总产品方向、技术约束与验收原则，供排期与实现对照。

---

## 1. 目标与原则

| 原则 | 说明 |
|------|------|
| PC 仍是主工作台 | 列表、统计、地图、票面、导出以桌面为准 |
| 采集可离开电脑 | 旅行途中手机录入；回家或联网后再与 PC 对齐亦可 |
| 入库质量不降级 | 凡写入 `train_ride_info` 的数据，须通过与手填相同的表单/校验路径 |
| 本地优先、控制成本 | 同步尽量不养重云；OCR 复用已有 CnOCR 环境，不先上专用票面大模型 |
| 不伪造成熟 | 菜单已宣传但未接通的能力（如 OCR 入口）应尽快产品化或改文案 |

---

## 2. 建议优先级总览

| 优先级 | 能力 | 说明 |
|--------|------|------|
| P0 | 手机录 ↔ 电脑看（同步） | 旅行场景刚需；省钱方案见 §3 |
| P0 | 行程字段：担当局 / 车段（可选）/ 车头或车底号 | 火车迷差异化；车站库已有「路局」，行程担当需另记 |
| P1 | OCR / 粘贴导入 → 预填表单 | 引擎配置已有，产品链路仍为 stub；见 §4 |
| P1 | 去过的站 / 路局覆盖、里程粗算 | 吃现有车站坐标与路局 |
| P2 | 车次主页、年度报告/成就 | 体验向 |
| P2 | 机车/车型打卡、行程附件图 | 文本 + 可选照片即可，勿先接全量机车库 |
| 工程债 | 地图二级菜单、Excel 导入、导出标签、数据清理、手册/更新检查 | 打磨项，穿插即可 |

**当前已较完整（不必重做）：** 行程增删改查与状态、标签、筛选、仪表盘、地图主流程、票面布局/PNG、导出、备份恢复、车站库（含路局）。

## 3. 手机端与 PC 双向同步

### 3.1 场景结论

「出门手机记、回家再 sync」在**桌面为主、手机补录**类工具中常见且合理。  
产品叙事应是「本地优先 / 对齐 PC」，避免宣传成「随时随地多端实时云协作」却依赖家里开机的电脑。

### 3.2 推荐技术栈（省钱、依赖好装）

| 层 | 选型 | 备注 |
|----|------|------|
| PC | 继续 WPF + .NET 8 + SQLite | 现有 GuiPiao |
| 手机 | **.NET MAUI** 或 **PWA** | 避开 Flutter/`pub`；与 C# 栈一致或浏览器即可 |
| 同步（首选） | PC 内嵌轻量同步服务 + Tailscale / Cloudflare Tunnel 等 | 作者几乎无月费；数据仍在用户本机库 |
| 同步（备选） | 用户自备 WebDAV / 坚果云等 | 仍可不养自有云库 |
| 同步（有付费用户后） | 小规格 ECS + ASP.NET Core API + PostgreSQL/SQLite | 短信验证码有成本，可先邮箱/配对码 |

**不推荐作主路径：** 整库拷贝 `guipiao.db`、纯 CSV 往返、Firebase/Supabase 当国内主叙事。

### 3.3 数据与不丢原则

- 同步单元：以 `TrainRideInfo` / `train_ride_info` 为主；标签及行程-标签一并同步；车站库一期可只读下发或后做。
- 现库缺跨端稳定 ID 与时间戳时，实施前需补：`sync_id`（UUID）、`updated_at`、软删/墓碑、（可选）`version` / `server_seq`。
- 协议形态：增量变更 + 幂等 `change_id`；字段级合并；同字段冲突进冲突箱；**同步前本地 DB 备份**（可接现有备份能力）。
- 设置/票面布局：默认不同步或单独开关，避免与行程合并搅在一起。

### 3.4 手机 MVP 范围

- 做：录入/编辑/列表、状态、简单标签、同步中心（待同步条数、上次时间、冲突）。
- 不做（MVP）：票面编辑、仪表盘、完整地图、复杂批量、多用户家庭共享。

## 4. OCR / 导入（行程采集辅助）

### 4.1 产品定位

- **主路径：** 截图 / 清晰票面照片 / 粘贴文本 → OCR 或直解析 → **预填现有新增/编辑表单** → **人工确认后保存**。
- **不主攻：** 退墨、褶皱、严重糊拍的旧纸票「抢救识别」；可降级为原文展示 + 手改。
- **清晰红/蓝票照片：** 要支持（客户拍照上传），与截图共用链路，不另起产品；质量差则低置信提示，不静默入库。

引擎：继续复用现有 Python + CnOCR / 设置页环境；缺的是「菜单 → 选图/粘贴 → 解析 → 打开表单」产品闭环（当前入口多为 stub）。

### 4.2 不要预制「每一种截图像素模板」

市面来源很多且 App UI 常变，**没有**可维护的官方截图 ROI 清单。应预制的是 **字段抽取**，不是 N 套版式坐标。

**来源族（粗分，仅作规则权重提示，分错不致命）：**

| 族 | 来源 | 解析难度 |
|----|------|----------|
| A | 12306 购票/改签短信 | 低 |
| B | 购票邮件 HTML | 低～中 |
| C | App「本人车票」列表卡 | 中 |
| D | App 订单详情 | 中（主战场之一） |
| E | 行程分享卡片 | 中～高 |
| F | 车站「行程信息提示」 | 中 |
| G | 纸质红/蓝票照片 | 清晰则中；退墨则高 |
| H | 微信/支付宝/携程等第三方 | 后做或不做 |

流水线：

```
图 / 粘贴 → 文本（OCR 或原文）
         → 通用字段抽取（车次、站、日期时刻、车厢座位、票价、检票口…）
         → （可选）来源粗分加权
         → 预填表单 → 人确认 → 与手填同一保存路径
```

建议实施顺序：① 粘贴短信/文本导入（打通闭环）→ ② 接现有 OCR 选图 → ③ 用语料补规则 → ④ 纸票清晰照作为输入之一。

### 4.3 如何保证结果「像手填一样可用」

识别**不得**另开写库路径。保证链：

1. **落点 = 现有新增/编辑表单**（同一 VM / `CreateTrainRideInfo` / Repository）。
2. **必填与格式 = 手填同一套校验**（站名尽量匹配车站库；失败标红不可存）。
3. **识别稿 ≠ 待提交稿**；默认「识别后编辑确认」，禁止静默入库。
4. **低质量降级：** 缺关键字段则打开表单并附原文；低置信字段高亮「请核对」。

验收标准：凡保存成功的记录，列表可展示/可搜索/可进票面预览，与手填合格数据无异。不要求 OCR 100% 正确。

### 4.4 语料

公开网页无法替代真实版式。落地前建议收集脱敏样本（短信全文、订单详情图、清晰纸票图等），按来源族标注期望字段，用用例驱动补规则。可建目录如 `Samples/Ocr/`（注意勿提交含证件号等敏感信息的原图到公开仓库）。

## 5. 火车迷向能力（补充）

### 5.1 行程侧元数据（优先）

在行程上增加（示意字段，实施时再定列名）：

- 担当路局（与车站「所属路局」不同）
- 车务段 / 客运段（可选）
- 车型备注、车头号或车底号（文本即可）

配套：筛选、仪表盘「坐过哪些局」、列表展示。

### 5.2 统计与成就

- 去过的站 / 覆盖路局 / 省份；有坐标则可做里程粗算
- 车次主页（同一车次多次乘坐聚合）
- 年度报告（本命车次、跨局次数、夜航等）

### 5.3 可后做

- 行程附件（车头图、站牌、票面）
- 经由示意、地图二级入口补完
- 完整交路图、实时正晚点、全量机车库、社区排行 —— 维护成本高，非必要

---

## 6. 明确不做或缓做（防范围膨胀）

- 以退墨纸票识别率当核心卖点
- 为每种 12306 App 版本维护像素级截图模板
- OCR/同步静默覆盖用户已有行程而不经确认
- MVP 阶段上票面编辑、云端多用户协作、端到端加密（可作为远期选项）
- Flutter 作为默认手机栈（依赖与镜像成本；若团队有充分理由另议）
